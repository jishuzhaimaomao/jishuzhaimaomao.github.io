# 思路借鉴篇：1、Codex如何做长任务下的上下文管理

> 本篇属于"思路借鉴"系列：不搬运代码，而是拆解成熟产品（这里是 OpenAI 的 Codex）在真实工程问题上的设计思路，提炼成可迁移到自己项目里的方法。第一期聊一个所有 AI Agent 都会撞上的难题——**长任务下的上下文管理**。

先把结论放在前面：**Codex 的思路不是把上下文窗口"塞得更大"，而是把上下文当成一种有预算、会衰减的资源来治理**——输入侧少装、对话侧摘要、过程侧落盘、任务侧隔离、记忆侧外置。本文先给一张治理总览图建立全局观，再沿"一次长任务的数据流向"逐层拆解机制，最后给出可抄的最佳实践清单。文末附本文借鉴的官方文档与论文出处。

## 1. 先看本质：上下文是"预算"，不只是"容量"

讨论上下文管理前，需要先建立一个更准确的模型。上下文窗口确实有 **token 硬上限**（容量问题），但对 Agent 质量影响更大的，是它的**边际效用递减与信噪比问题**：

- **越长越"看不清"**：研究表明模型对长上下文的利用并不均匀，对放在中间位置的信息召回明显弱于开头与结尾（即著名的 "Lost in the Middle" 现象）。上下文越长，关键信息越容易被淹没。
- **成本随长度非线性上涨**：每次请求都要重新处理全部历史 token（prefill），长任务往往有几十上百轮请求，`总成本 ≈ Σ(每轮上下文长度)`。上下文不清，成本呈近似平方级增长。
- **位置即权重**：在同一份上下文里，"放哪儿"几乎和"放不放"一样重要——系统提示在最前、最新观察在最后，都是把信息放在模型注意力更强的地方。

因此"上下文管理"实际上是在做四件事：**少放（输入治理）、精放（历史治理）、放对位置（结构治理）、放不下就外置（状态与记忆治理）**。Codex 的机制正好一一对应这四件事。

## 2. 上下文管理总览：五层治理结构

下面这张总览图展示了 Codex 在长任务中治理上下文的核心结构：一条"组装 -> 执行 -> 交付"主链路，外加输入治理、对话治理、状态治理、执行治理、记忆治理五个子系统。

![Codex 上下文管理总览图](/blog-assets/codex-context-overview.png)

对照图可以把五个机制记成一句话：

| 治理层 | 核心动作 | 回答的问题 | 一句话原理 |
| --- | --- | --- | --- |
| ① 输入治理 | 分级、按需注入 | 哪些知识必须进上下文？ | 默认少装，用到才读 |
| ② 对话治理 | 滚动窗口 + 自动压缩 | 历史放不下怎么办？ | 老历史摘要化，近期保留原文 |
| ③ 状态治理 | 计划 / 检查点外置 | 摘要丢了关键决策怎么办？ | 状态存在结构化对象里，不靠对话记忆 |
| ④ 执行治理 | 子代理隔离上下文 | 一个窗口装不下所有子任务怎么办？ | 子任务独立上下文，主线只收结论 |
| ⑤ 记忆治理 | 跨会话外部存储 | 这次任务的经验下次怎么用？ | 长期记忆落盘，需要时按需检索 |

## 3. 长任务下的数据流向：一个回合的生命周期

总览图是"静态架构"，数据流向图则是"动态过程"——看一次长任务中，请求、工具结果、计划、记忆是如何流动的，以及五个治理动作分别发生在什么时机。

![Codex 长任务上下文数据流向图](/blog-assets/codex-context-dataflow.png)

沿时间轴拆解这张时序图：

1. **组装阶段（每轮请求前）**：上下文组装器按当前作用域注入规则与技能，并从长期记忆里按相关性检索有用经验——而不是把全部记忆灌进去。此时还会检查窗口水位。
2. **推理/行动循环**：LLM 发出 tool_call，工具/子代理执行并回填 observation，模型继续下一轮。**每完成一步，计划与检查点被更新**——这是"状态治理"发生的时刻，它让模型不必在下一轮靠回忆来确认进度。
3. **水位接近上限**：自动压缩器介入，把早期历史摘要化并回填到窗口，同时**保留最近未压缩的原文**，保证正在进行的操作不失真。
4. **收尾**：关键经验提取入长期记忆；会话持久化，保证可以被恢复、续跑。

注意图中的一个关键设计：**治理动作大多发生在"窗口之外"**——计划、记忆、规则都不住在对话历史里。它们只在组装阶段被"投影"进窗口，用完即走。这正是对抗摘要损失的根本手段。

## 4. 机制深拆：五层治理如何对抗上下文膨胀

### 4.1 输入治理：把"知识装载"从加法改成按需

很多自研 Agent 的第一步就是把所有文档、规则一次性拼进 system prompt。Codex 的输入治理是反过来的：

- **AGENTS.md 目录作用域**：仓库规则按目录生效，只有与当前改动相关的子树规则进入上下文。改 `src/pages` 时，不需要把 `docs/` 的规范一起背着。
- **Skill 懒加载**：技能在上下文里只占"名称 + 触发条件 + 一句话说明"，命中用户请求后才把完整指令读入。上下文常驻成本是 O(技能数)，而不是 O(全部技能正文)。
- **文件按需读取**：需要看哪个文件就读取哪个，命令输出也只保留对当前决策有用的部分。

> 工程实质：这是把**检索**前置到了提示词构造阶段。可以把它理解成一个确定性的"迷你检索器"——判定条件来自当前任务的作用域，而不是模型的注意力。

### 4.2 对话治理：滚动窗口与有损压缩的平衡

历史对话是窗口最大的消耗者。Codex 的做法是：**滚动窗口 + 自动压缩**，触发点在接近窗口上限时，而不是等到报错。

这里要理解一个本质权衡：**摘要是有损压缩**。任何"压缩历史"都会丢失细节，压缩比越高、丢得越多。Codex 的设计通过两个手段缓解损失：

1. **分层保留**：压缩只针对"老"消息，最近几轮原文始终保留。因为对正在进行的任务而言，最近的工具结果、最近的报错，信息密度最高。
2. **摘要做"索引"而非"全文"**：被压缩掉的历史，其关键结论会同步沉淀到结构化状态（见 4.3）和记忆（见 4.5）。摘要只负责让模型"知道发生过什么、去哪找细节"，而不是成为细节的唯一载体。

> 工程实质：这套组合非常像分布式数据库的 **WAL + Log Compaction**——结构化状态是无损的"预写日志"，摘要则是压缩后的"快照"。两者配合，才既控制体积又不丢关键信息。

### 4.3 状态治理：把"状态"从对话里搬进对象里

自研 Agent 最常见的反模式，是让模型"记得"任务状态——写到第几步、哪个方案被否了、等待谁确认。对话一压缩，这些记忆就蒸发了。

Codex 的答案是**显式的计划与检查点对象**：

- 任务开始先生成结构化计划（步骤、验收标准）；
- 每完成一步就更新计划对象（标记完成、记录产物引用、记录决策原因）；
- 恢复任务时，先读计划对象对齐现场，而不是重放历史。

为什么这样能扛住压缩？因为**状态的生命周期不依赖对话历史**。对话被摘要化后，模型丢失的只是"过程的叙述"，而"当前的结论"仍在对象里、可随时读回。

> 工程实质：这是把 Agent 从"无状态对话函数"改造成"有状态工作流"。建议状态对象至少包含：目标、已完成步骤及产物、当前步骤、已知约束与决策原因、下一步动作、阻塞项。

### 4.4 执行治理：用子代理隔离上下文，主线只收结论

当任务本身巨大（一次改完一个模块、并行处理多个独立子问题），即使做了前几层治理，单窗口仍会不堪重负。Codex 的做法是把子任务**委托给独立上下文的子代理**：子代理在自己的窗口里专注干活，完成后把改动与结论合并回主线。

从成本模型看这为什么划算。假设主线已有 `N` token 上下文，某个子任务需要 `K` token 的上下文才能完成：

- **单窗口硬做**：主线程上下文变成 `N + K`，且后续每轮都要重新处理这 `N + K`——既可能超限，也让主线注意力被子任务细节稀释。
- **子代理隔离**：子代理为这次任务支付 `K` 的独立成本，主线只追加"子任务的结论摘要"（远小于 `K`）。主线上下文保持 `N + 摘要`，且两者互不污染。

隔离还带来一个隐藏收益：**避免串扰**。如果两个子任务共享一个窗口，任务 A 的失败尝试可能成为任务 B 的噪声，甚至误导 B 的决策。隔离后，A 的试探与重试不会出现在 B 的上下文里。

> 工程实质：这是"上下文作用域"的运行时版本。设计多代理系统时，关键是明确**什么进主线、什么进子代理**——目标与验收留主线，过程与细节下放子代理，回传物必须是"结论"而非"日志"。

### 4.5 记忆治理：按生命周期分层的记忆系统

把所有信息都塞进"当前对话"是最昂贵的存法。Codex 把信息按生命周期拆到不同层级：

| 记忆层 | 生命周期 | 载体 | 什么时候读回 |
| --- | --- | --- | --- |
| 工作记忆 | 单轮任务 | 对话窗口 + 计划对象 | 每轮请求 |
| 会话记忆 | 单次会话 | 压缩摘要 + 会话存档 | 会话续跑时 |
| 长期记忆 | 跨会话 | 文件 / 数据库（技能、AGENTS.md、用户记忆） | 组装阶段按相关性检索 |

这个分层的价值在于：**每层只存最合适的信息，且都按需读回，而不是常驻窗口**。长期记忆层的写入时机（任务收尾、关键决策产生时）与检索时机（新任务组装时）是显式设计的——这与 MemGPT 等研究中"把记忆当操作系统内存分页管理"的思路一脉相承。

## 5. 技术纵深：把上下文当预算做工程化

理解了机制，再往工程化走一步：如何把"治理上下文"变成一个可量化、可监控、可测试的系统？

### 5.1 给每类内容分配预算

与其让上下文"自然生长"，不如先设一个预算表，每类内容有明确上限：

| 内容类型 | 建议预算占比 | 说明 |
| --- | --- | --- |
| 系统提示 + 全局规则 | 5%~10% | 尽量精简，常驻 |
| 作用域规则 / 技能正文 | 10%~20% | 只装当前任务命中项 |
| 检索回来的记忆 | 5%~15% | Top-K 截断，宁可少而准 |
| 滚动窗口（近期原文） | 40%~50% | 最近几轮工具结果与对话 |
| 压缩摘要（老历史） | 5%~15% | 老历史只保留索引级摘要 |

预算表的价值不是精确，而是**让"超支"变得可见**——组装后如果总长度超预算，说明某个治理环节失效了。

### 5.2 触发式压缩而非定时清空

压缩的触发条件应当基于**可观测的水位**（已用 token 数 / 窗口上限），配合安全阈值（如 70% 触发、85% 强制）。同时为压缩结果定义明确的摘要 schema，例如：

```text
目标：<正在完成的任务>
已确认的事实：<验证过的结论，含文件/命令/commit 引用>
已做的决策与原因：<为什么选 A 不选 B>
当前状态：<进行到哪一步>
阻塞 / 待确认：<等什么>
下一步动作：<接下来做什么>
```

字段化的摘要比自由文本更可靠——因为**后续环节可以把这些字段读回结构化状态**，而不是让模型从一段散文里再"理解"一遍。

### 5.3 把"恢复"做成第一公民

长任务的上下文管理最终要支撑一件事：**任务可以被中断、被恢复、被 fork**。这意味着：

- 每次状态更新都持久化（计划、检查点、产物引用）；
- 恢复时通过"会话/检查点 ID"重建现场，而不是重放全部历史；
- 归档机制让旧会话可以被安全保留和检索。

Codex 的会话存档、恢复、派生（resume / fork）就是这套能力的体现。自研系统里至少要做到：**崩溃后重开任务，Agent 能说出"我进行到哪一步、下一步做什么"**——做不到这一点，上下文管理就不算闭环。

### 5.4 质量与可观测性

- **压缩质量评估**：对关键长任务做"压缩-重建"测试——压缩后让模型回答几个只有原文里才有的细节问题，统计召回率，作为摘要质量的回归指标。
- **水位监控**：记录每轮请求的 token 构成（规则占多少、历史占多少、工具结果占多少），报警异常增长。
- **黄金用例**：为最容易丢信息的场景（长任务中断恢复、多文件重构、跨天续跑）建立端到端测试。

## 6. 最佳实践：一份可参考的清单

综合上面的分析，给自研 Agent 的工程实践按优先级排序：

### P0 · 地基

1. **引入结构化状态对象**：任何多步任务先写计划，每步完成即更新。状态含目标 / 进度 / 决策原因 / 下一步，独立持久化。这是后续一切治理的前提。
2. **做触发式自动压缩**：监控已用 token 占比，70% 触发、85% 强制；摘要用固定字段 schema；保留最近若干轮原文。
3. **让状态先于摘要**：压缩前确保关键决策已写入结构化状态；摘要永远只当"索引"，不当细节的唯一载体。

### P1 · 减负

4. **知识分级装载**：区分"全局常驻 / 作用域注入 / 按需检索"三级；大段规则改成"名称 + 触发条件"，命中再读全文。
5. **记忆外置 + 按需回读**：长期经验写入数据库；新任务组装时按相关性检索 Top-K，而不是常驻窗口。
6. **设置内容预算表**：给系统提示、规则、历史、记忆分配预算占比，超支即告警。

### P2 · 规模化

7. **子任务隔离**：可独立完成的子任务下放给子代理/独立上下文，主线只接收"结论摘要"。
8. **恢复第一**：会话可存档、可恢复；崩溃重开时 Agent 能自述进度与下一步。
9. **建立质量护栏**：压缩重建测试、token 构成监控、关键场景黄金用例。

```text
推荐的最小闭环（可直接照做）：
每轮组装 = 常驻系统提示
         + 当前目录作用域规则
         + 压缩摘要（字段化）
         + 最近 N 轮原文
         + 检索到的 Top-K 记忆
每轮结束 = 更新计划对象 → 判断水位 → 必要时压缩
任务结束 = 提取关键经验入库 → 会话归档
```

## 7. 常见误区与取舍

- **只压缩、不外置**：摘要丢细节后无处可查，等于把"细节"永久删除。先外置再压缩。
- **窗口够大就不用治理**：窗口变大缓解容量问题，但放大不了注意力——Lost in the Middle 不会因为窗口变大而消失。
- **子代理越细越好**：子代理有调度与回传开销，粒度过小反而亏。只有当"子任务上下文成本 + 调度开销"小于"塞进主线带来的污染成本"时才划算。
- **记忆无条件写入**：记忆污染比没有记忆更糟——写之前问"这条经验是否可复用、是否已验证"。可参考反思类范式，只沉淀验证过的结论。
- **压缩阈值拍脑袋**：不同任务的"历史敏感度"不同。代码重构任务对最近几步极其敏感，应提高保留轮数；资料调研类任务对早期事实敏感，应提高摘要质量权重。
